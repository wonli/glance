# PDF File Backing Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:executing-plans` for Native execution; if the user selects Subagent-driven execution, use `superpowers:subagent-driven-development`. Steps use checkbox syntax for tracking.

**Goal:** Restore and browse large workspace PDFs without loading the entire SQLite payload into Go heap, while preserving exact recovery snapshots.

**Architecture:** Stream the existing SQLite BLOB in fixed-size chunks under one read transaction into an owned temporary snapshot, then let `pdfdoc.Document` retain a read-only mmap backing on macOS/Linux. Keep collection metadata independent of payload hydration, restore PDFs in a managed background task, and persist full bytes only when the initial snapshot is missing or the PDF revision changes.

**Tech Stack:** Go, `database/sql`, pinned `modernc.org/sqlite` low-level `lib`/`libc` interfaces for incremental BLOB reads, standard-library `syscall.Mmap`/`Munmap`, existing Gio background-result and workspace-writer paths.

**Spec:** [2026-10-21-pdf-mmap-design.md](../specs/2026-10-21-pdf-mmap-design.md)

## Global Constraints

- The existing SQLite `documents.payload` remains the authoritative recoverable snapshot; copy every byte unchanged and make no schema migration.
- Use 1 MiB `sqlite3_blob_read` chunks within one SQLite read transaction; do not use SQL `substr` or `SELECT payload`, which do not provide a reliable bounded-memory guarantee.
- Use read-only mmap on macOS/Linux and a compiling compatibility fallback on other targets; a mmap failure on a supported target returns an error.
- Keep SQLite streaming, tempfile writes, PDF parsing, and mmap construction out of Gio frame/layout code.
- Keep the PDF backing alive until `Document.Close`; close is synchronized with all reader operations and unmaps only after reader/history references are cleared.
- Preserve existing `OpenSnapshot` and `OpenSnapshotOwned` ownership semantics and existing atomic source-file save behavior.
- Do not retain complete PDF payloads in `Collection.Session.Payload` after PDF persistence; preserve other format cache behavior.
- Check the published PDF revision before requesting snapshot bytes; a clean view-state write must not clone the PDF into Go heap.
- A failed database write must not advance the persisted PDF revision or clear dirty state.
- The active mapped snapshot occupies temporary disk space approximately equal to the PDF size until `Document.Close` releases the mapping.
- Do not add dependencies or change PDF format support claims beyond documenting the backing and fallback behavior.

## Review Focus

- **SQLite chunk boundary and snapshot consistency:** test multi-chunk/tail bytes, writer failure, and an update from a second WAL connection after the first chunk; the streamed result must remain the original transaction snapshot. Task 2 owns these tests.
- **Backing cleanup on every exit:** test writer failure, invalid PDF, repeated close, and temp-path removal; no mapping may outlive its document. Task 1 owns these tests.
- **Restore result arriving after navigation:** test switching or closing a tab while the PDF worker is still running; the stale document must be closed and never installed. Task 3 owns this test.
- **Clean persistence versus changed revisions:** test that a clean view-state update leaves payload bytes untouched, while an edited revision is written once and failure leaves retry/dirty state intact. Task 4 owns these tests.
- **Source-file snapshot and compatibility:** test that replacing the original path after open does not change the reader's bytes, save/reopen and undo preserve current behavior, and non-mmap targets compile. Tasks 1 and 5 own these checks.

### Task 4: Revision-aware PDF workspace persistence

**Files:**
- Modify: `internal/desktopui/document_session.go`

- Modify: `internal/workspace/collection.go`
- Modify: `internal/workspace/store.go`
- Test: `internal/desktopui/pdf_workspace_persistence_test.go`

**Interfaces:**
- Store the PDF snapshot-present flag and persisted revision in the shared session; guard persistence decisions and updates with a dedicated `pdfPersistenceMu`, so concurrent windows cannot duplicate or reorder checkpoints.
- Consume `pdfdoc.Document.SnapshotWithRevision()` from Task 1 so persisted bytes and revision are one atomic snapshot when a changed revision needs writing.
- Route both background and synchronous workspace-write paths through the same PDF persistence decision while holding the adapter read lock for the revision check. Compare the cheap published `Document.Info().Revision` first; use `Collection.UpdatePDFMetadata` when snapshot presence is true and revisions match, without calling any snapshot method. Otherwise call `SnapshotWithRevision()` under the same adapter read lock and write that exact revision with `Collection.UpdatePDFSnapshot`.
- Mark a revision persisted only after Store success; a restore from SQLite seeds the persisted revision, while a source-file open without a workspace BLOB starts with snapshot-present false.
