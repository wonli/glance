# Word 版本历史设计

## 目标与已确认约束

为 Word 增加本地版本历史，让用户能查看 DOCX 的已保存状态，并将旧版本恢复为一次可撤销的编辑。历史快照保存在 Glance 自己的 SQLite 工作区；不依赖 LibreOffice 或其他外部 Office 程序。桌面入口保持 `go run ./cmd/desktop`。

用户已批准以下规则：

- 保存完整 DOCX 快照，按文档路径分别保存历史；关闭文档标签不删除历史。
- 首次打开文档时建立基线。成功的手动保存仅在内容改变时增加版本。
- 自动保存版本至少间隔 5 分钟；重复内容去重。
- 每个文档最多保留 50 个版本或 512 MiB 快照数据，达到任一限制时从最旧版本开始清理。
- 恢复前先留存当前版本，再将所选快照作为一次可撤销的 Word 编辑应用。

本文中的假设：历史版本的内容来自已经成功打开或写入的 DOCX 包；自动保存只有在源文件写入成功后才可生成版本。历史数据库故障不能回滚已成功的源文件保存。

## 方案比较与选型

### 方案 A：完整快照保存在工作区 SQLite（采用）

为工作区数据库新增 Word 版本表，每个版本存一份完整 DOCX 包快照及时间、触发来源和大小。该方案能保留未知 OOXML 部件，能在恢复时完整重建 DOCX，也符合本应用现有的本地工作区存储方式。

### 方案 B：只保存 Word 文本或差异

占用空间较少，但不能可靠恢复图片、关系、样式、元数据和未支持的 OOXML 内容；差异链损坏也会影响后续版本。与完整恢复目标不符，不采用。

### 方案 C：依赖外部版本服务或 Office 程序

需要网络服务、额外部署或外部应用，与本地独立桌面软件约束不符，不采用。

## 用户行为

- 文件功能区“版本历史”打开当前 DOCX 的版本列表，显示时间、来源（首次打开、手动保存、自动保存、恢复前留存）和快照大小，并按最近时间倒序排列。
- 选择版本后必须再次确认恢复。恢复成功后关闭历史面板，将该 DOCX 全包快照作为一个 Word 编辑应用；当前源文件不立即改写，文档变为 dirty，之后走现有保存流程。
- 恢复操作之前先将当前内存文档快照写入版本历史。若该写入失败，取消恢复并保留当前文档不变。若恢复应用失败，当前文档也必须保持不变。
- 恢复后的单次 Undo 回到恢复前的完整文档状态；Redo 再次应用所选版本。此操作不清空既有撤销/重做历史。
- 无路径草稿在成功“另存为”到 DOCX 之前不显示历史；首次成功写入目标路径时为该路径建立基线。另存为不同路径会使用独立历史，旧路径历史保留。
- 关闭标签页只结束当前会话，不删除版本。版本仅因每文档保留上限而淘汰；本设计不增加手动删除版本入口。

## 版本与内容身份

- Word 历史以规范化后的绝对文档路径为键；实现复用应用现有的路径规范化规则。不同路径对应独立历史。文件移动或重命名不会自动迁移历史。
- 首次打开时，从应用读入原文件后取得基线快照；如果源文件不可用而只能恢复工作区快照，则以该快照建立基线并标记来源为“恢复基线”。已存在历史时不重复建立基线。
- 快照是完整、独立可打开的 DOCX ZIP/OOXML 包，而不只是文档正文 XML。恢复应保留当时快照中的图片、关系、样式、元数据及其他包部件。
- 为判断内容是否相同，按包部件名称排序后，对每个部件的未压缩数据计算稳定指纹；压缩级别、ZIP 时间戳和条目排列差异不应制造新版本。所有包部件都参与比较，包括未知部件。
- 手动/自动保存及恢复前留存均与该文档最近版本比较。若完整包内容相同，不插入新版本；这会去掉连续的无变化保存，但内容从 A 变为 B 再回到 A 时会新增一个时间点，以保留版本时间线。

## 架构与数据流

```text
Word ribbon / controller
       ├── list and restore intents
       └── successful manual/autosave results
                 ↓ immutable DOCX bytes
DOCX adapter ── Snapshot / apply-one-undoable-snapshot
                 ↓
workspace Store ── SQLite transaction: insert → enforce limits → commit
```

### Workspace store

- 将 SQLite schema 迁移到下一版本，新增 `word_versions` 表，至少保存版本 ID、规范化文档路径、触发来源、创建时间、快照字节数、内容指纹和完整 DOCX 快照 BLOB。
- 文档路径与时间需要可索引；在同一事务中执行内容去重、插入、计数/字节统计和最旧版本淘汰，避免并发保存产生超限或丢失引用。
- 版本查询只返回列表元数据；用户选择一项后再读取其 BLOB，避免列表阶段装载所有快照。
- 50 个版本和 512 MiB 以单个规范化文档路径当前保留的快照计数及 BLOB 字节数计算。超任一限制时从最旧版本开始删除，直到两项均满足；始终保留最新版本。
- 单个快照大于 512 MiB 时不写入历史，并返回可显示的明确错误；不删除既有历史，也不阻止源 DOCX 的打开或已成功保存。
- 快照写入失败时 SQLite 事务回滚，确保不会留下没有快照的列表记录或半完成的淘汰操作。

### Controller 与保存集成

- 基线建立、版本列表读取、快照写入和清理都在后台工作队列/工作区写入路径中执行，不放在 Gio layout/frame 调用中。首次打开时先在后台持久化基线，再发布可编辑会话，确保后续保存排在基线之后；如果基线写入失败，仍打开文档，但显示历史记录错误。
- 只有源 DOCX 的手动保存已成功原子写入后，才提交“手动保存”版本。已有保存失败语义保持不变：文件未成功保存时 dirty 状态不清除，也不增加版本。
- 自动保存使用单独的每文档上次自动版本时间。若与上次自动版本间隔不足 5 分钟则跳过；达到间隔后，在下一次成功的自动文件写入上检查完整内容并去重。手动保存不受自动保存限频影响。
- 若文件写入成功但历史持久化失败，文件仍视为保存成功且 dirty 状态照常更新；状态栏明确提示历史版本未能记录，并允许后续保存/恢复操作重试。
- 版本历史 UI 只对 DOCX 会话可用。版本读写错误不应导致关闭、切换或恢复其他标签页失败。

### DOCX snapshot 恢复

- DOCX adapter 提供一个原子“以完整快照替换当前包并作为一次 Word 历史编辑”操作。它必须校验快照可解析，再一次性切换包部件、neutral Word 投影和相关索引；校验失败不得修改当前状态。
- 替换操作进入既有 Word undo/redo 模型，且只占一个 undo 步骤。撤销后恢复替换前整包状态；重做后恢复目标快照。
- 成功恢复将文档标记 dirty，但不写源文件。现有保存、自动保存和另存为按正常流程处理结果。
- 应用版本前，控制器先复制当前 Word 内存状态的不可变快照并写入历史；成功后才请求 adapter 执行恢复。若源文件在恢复期间被外部修改，不在此功能中自动覆盖磁盘文件；之后正常保存仍按现有外部变化策略处理。

## 失败处理与数据安全

- SQLite 打不开或迁移失败时，文档编辑与文件保存继续可用；版本历史显示具体不可用原因。不得把内存中暂存的版本静默显示成已持久化历史。
- 历史达到预算时，在事务中删除最旧版本；数据库事务失败则完整回滚，不部分执行清理。
- 读取快照或 adapter 校验失败时，保持当前编辑器内容、dirty 状态、undo/redo 栈和源文件不变，并展示具体错误。
- 在恢复前版本未成功持久化时不应用恢复，确保用户可以撤销回到恢复前内容。
- 历史快照属于本地工作区数据，不自动上传或放入最近文件列表。用户保存 DOCX 时仍只写当前活动版本。

## 验收与测试

### Workspace 持久化

- 迁移测试覆盖旧版数据库升级、重开数据库后版本与快照仍存在、按路径隔离、标签关闭后历史保留。
- 事务测试覆盖完整插入、相同内容去重、快照写失败回滚、计数/字节任一超限清理最旧项，以及超大单快照拒绝且保留既有历史。
- 比较测试证明只改变 ZIP 压缩信息或条目顺序不会新增版本；任意包部件的内容变化（包括未知部件）都会改变指纹。
- 保存集成测试覆盖首次打开基线、成功手动保存、失败保存不增加历史、自动保存不足 5 分钟不新增、达到间隔后新增、手动保存不受限频影响。

### DOCX 恢复

- 选择版本恢复后核对正文、图片、关系、样式和未知包部件；恢复后标脏、源文件在显式保存前字节不变。
- 一次 Undo 恢复恢复前状态，一次 Redo 再应用目标版本；两者都保留正确 dirty 状态。
- 覆盖历史写入失败、快照损坏、adapter 校验失败、版本已被淘汰和当前文档与目标版本相同等边界，确认失败路径不改变活动文档。
- 将恢复后的文档保存到 DOCX 并重开，核对恢复内容和代表性未改部件；不得调用 LibreOffice。启动命令使用 `go run ./cmd/desktop`。

### UI 与 Computer Use

- 用 Computer Use 对照 Pen 的 Word 页面/文件菜单，核对“版本历史”入口、列表层级、选择与确认恢复流程；使用一致窗口尺寸与缩放，记录截图和偏差。
- 验收至少覆盖空历史、一个版本、含多个来源版本、恢复确认和错误状态。版本列表为空时说明“保存 DOCX 后开始记录”，不可伪造版本。
- 自动化测试验证事件与状态；Computer Use 验证真实菜单/弹窗的可见结构和操作顺序。应用启动成功本身不构成视觉验收通过。

## 实施后文档维护

功能落地时更新 `docs/word-ribbon-todo-zh.md`、`docs/office-support.md` 及兼容性矩阵。只有基线、保存记录、限频/去重、预算清理、完整恢复、undo/redo、错误状态和 Computer Use 验收都有证据后，才把版本历史标记为完成。
