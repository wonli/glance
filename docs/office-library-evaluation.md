# Office Library Evaluation

Status: initial implementation dependencies selected and evaluated on 2026-09-28. `go.mod`/`go.sum` are the version authority; the feature boundary and evidence are in [office-support.md](office-support.md).

## GUI dependency

Use **Gio v0.10.2**, the latest released `gioui.org` version checked on 2026-09-28, as requested. The desktop command is isolated at `cmd/desktop`. The XLSX surface is drawn directly by Gio; it does not depend on a web view or third-party Office widget.

Source checked: [gioui.org/app on pkg.go.dev](https://pkg.go.dev/gioui.org/app).

## Selection principles

1. Separate parsing/editing from rendering. A Go library that reads OOXML does not provide an Excel/Word editor UI; Gio owns interaction and drawing.
2. Prefer separate XLSX and DOCX adapters if that gives better capability and preservation. A single multi-format library is not automatically better.
3. Pin versions and record license, Go/cgo requirements, supported features, known omissions, and measured behavior in this file when a dependency is selected.
4. Prove save/reopen behavior before enabling overwrite. Read tests alone do not establish safe editing.

## Candidates to validate

### XLSX: Excelize (selected)

The implementation uses `github.com/xuri/excelize/v2 v2.11.0`. The adapter exposes bounded cell windows, common styles, merge ranges, row heights, column widths, and ordinary over-cell pictures through neutral DTOs. Visible formula cells are evaluated through Excelize `CalcCellValue` where supported; this is display-only, is not a workbook-wide recalculation, and does not persist formula caches. Excelize documents unsupported formula categories and incomplete calculation support, so Excel parity is not established. `internal/format/xlsx/pictures.go` uses the public picture read/add/delete surface behind the adapter; tests show that `GetPictures` returns drawing scale rounded to two decimal places and `DeletePicture(sheet, cell)` targets a cell rather than one drawing, so same-anchor pictures are read-only. The first slice does not preserve full DrawingML anchor geometry or promise exact Excel layout. Synthetic picture fixtures cover insert/replace/move/resize/delete, undo/redo, save/reopen, and unrelated content preservation. The local employee-performance sample has malformed `xl/styles.xml` (`<font>` closed by `</name>`) and is not an Excelize-readable evidence source. Universal unsupported-part preservation is not established.

Sources: [Excelize documentation](https://xuri.me/excelize/en/index.html), [source repository](https://github.com/xuri/excelize).

### DOCX: project-local OOXML adapter (selected for the first slice)

`internal/format/docx` uses Go ZIP/XML libraries for neutral ordered body projection and targeted text, formatting, alignment, paragraph-indentation, and inline-image operations. The adapter now also projects common section page geometry, style/default inheritance inputs, paragraph spacing/line rules/indents/keep flags, and table grid/cell widths as read-only neutral data. Focused fixtures verify twips/EMU/point conversion, explicit-off formatting masks, unsupported section/table diagnostics, and unchanged DOCX snapshot bytes. This is projection evidence only: it does not establish page layout, pagination, floating-image layout, or broad Word fidelity. The Gio renderer still handles body paragraphs, tables, and inline raster previews in continuous flow.

### Legacy Word `.doc` import: macOS system `textutil`

There is no new runtime, Go, or cgo dependency. The macOS desktop worker takes a private on-disk snapshot of the `.doc`, calls `/usr/bin/textutil -convert docx` on that snapshot, validates the resulting ZIP, and opens the same project-local DOCX adapter used by native `.docx`. Both staged files are removed after package load. The source `.doc` stays protected from Save/AutoSave; edits require Save As `.docx`. Staging is disk-backed, but both binary metadata recovery and DOCX package loading use memory proportional to the loaded file.

A project-local bounded CFB/FIB/CLX/SEPX/PAPX reader now recovers single-section Word 97+ page dimensions, margins, vertical document-grid pitch, direct paragraph spacing, paragraph page-break/snap overrides, and main/header-story boundaries. It rejects out-of-stream offsets and cyclic storage. Before relocating converter-appended header/footer paragraphs, the adapter requires every source main-story paragraph to match the converted text. Recovered header/footer fields remain separate OOXML story parts, including their field instruction/result delimiters; their instructions no longer become body text. Unsupported multiple sections, footnotes/endnotes/annotations/textbox stories, tables or unmatched body projections retain the system conversion without this repair. This is a metadata recovery subset, not a complete binary Word parser; typography, style inheritance, embedded content, and footer preview remain subject to the converter and shared renderer boundaries.

Font recovery additionally reads bounded FFN and CHPX records for uniform direct paragraph font slots. It restores the original names in staged DOCX without changing other run properties; mixed/inherited font mappings remain on the system-converter path. Shared DOC/DOCX shaping retains separate script fonts and uses localized aliases plus platform substitutes. Missing SimHei (黑体) preserves its half-em ASCII layout for single-glyph clusters; other font substitution remains approximate. Installed original fonts are never rescaled. The three source form labels use 12/16/26 ordinary spaces, not tabs; independently checked accepted scenes and reopened DOCX align the two lower right labels while preserving the source's approximately half-character offset on the first.

Independent sample evidence on 2026-10-14: `税收征收管理电子数据互信协议书.doc` has 30 main-story paragraphs, A4 geometry and a 312-twip line grid, with no inline manual page break. `TestLegacyDOCIndependentSamplePagination` runs the actual desktop installation/accepted-scene path, checks two A4 pages with clauses III–V and the signature on page 2, saves/reopens DOCX with the same layout, and checks that source bytes remain unchanged. The opt-in `GLANCE_DOC_PAGINATION_SAMPLE` path keeps the user's document outside the repository. Its accepted-scene PDF was rasterized and inspected; this does not establish Gio window pixel verification or exact WPS typography/wrapping. Synthetic native-reader and OOXML repair fixtures cover malformed offsets, storage cycles, explicit breaks, story separation, mismatch no-ops and save/reopen. Windows and Linux still report `.doc` import unsupported.

References: [MS-DOC section properties](https://learn.microsoft.com/en-us/openspecs/office_file_formats/ms-doc/46c3ec54-53ff-4c0a-b0d6-07ad15d2546e), [MS-DOC header stories](https://learn.microsoft.com/en-us/openspecs/office_file_formats/ms-doc/8465bee7-6c79-45a9-812e-58b0c5fd6cdc), and [OOXML document-grid line pitch](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.wordprocessing.docgrid.linepitch?view=openxml-3.0.1).

### PPTX: go-pptx/v2 behind the local adapter

`go.mod` pins `github.com/F31/go-pptx/v2 v2.0.3`; third-party presentation and OOXML types stay inside `internal/format/pptx`. `TextFrame.SetPlainText` is not used for edits because its documented behavior removes character formatting, fields, and links. The adapter edits one paragraph through `Paragraph.ReplaceText`, whose paragraph patch is transactional and inherits the leading character's style. It fails closed for multi-paragraph text boxes, fields, special breaks, and unsafe linked/run structures.

The pinned library does not expose a classic PowerPoint comment editing API. `internal/format/pptx` therefore adds and deletes only the required classic `commentAuthors`, per-slide comments, OPC relationship, and content-type parts as targeted package edits after library serialization. The comment XML is patched in place to preserve unknown sibling content, and the staged package is checked before replacement. The implementation does not edit newer PowerPoint comment parts and rejects mutations when those are present. `TestPresentationCommentCapabilitySavesAndReopensWithoutLosingSlideContent` verifies a Glance-generated deck can save, close, reopen, and retain the classic comment plus existing slide text. Interoperability with PowerPoint and LibreOffice remains unverified.

Evidence: `internal/desktopui/presentation_workspace_test.go` exercises canvas click, editor focus, typing, unsaved-draft tracking, toolbar save, and reopen on a disposable deck. `TestPresentationTextEditorKeepsSelectionFrameAndSupportsTransforms` verifies the editor frame equals the object geometry and that move/resize/rotation keep text editing active. `internal/format/pptx/document_test.go` edits the supplied `1.pptx` title on a temporary copy, reopens it, checks its Arial 37.2pt bold/color style, checks an untouched slide 2 text shape, and compares source file bytes before and after. Evidence is limited to these samples and operations; other DrawingML features and imported-deck Gio interaction remain unverified. Drafts commit on save or when switching shapes/slides rather than on each frame; package serialization stays in the save path.

Agent-only slide duplication uses the pinned library’s same-document `Slide.Clone` API with its default media-sharing policy. The dependency documents that charts/workbooks are copied independently and unknown internal relationships are rejected, but Glance’s cache projection and save/reopen integration for this command remain unverified. For top-level text shapes, auto-shapes, and pictures, the pinned library exposes no geometry mutation API. The adapter therefore retains neutral point-based transform overrides and applies shape-ID-targeted DrawingML `a:xfrm` patches after library serialization for both Save/Save As and recovery snapshots. The patch path preserves existing flip/lock attributes, materializes inherited placeholder geometry on the edited slide, validates by reopening, and replaces a source only after a successful write. `TestPPTXCanvasTransformSaveReopenPreservesUntouchedContent`, `TestTransformSnapshotBytesRetainsGeometry`, `TestTransformPatchPreservesLocksAndFlips`, `TestInheritedPlaceholderTransformMaterializesLocally`, and `TestTransformSaveFailurePreservesOriginal` are the evidence for this boundary. This supports bounded transform edits; it does not establish group-transform, crop, style, unsupported-extension, or general PowerPoint fidelity.

The local adapter also parses OPC slide→layout→master relationships directly and projects effective slide backgrounds, supported theme color mappings and indexed solid/image background styles, exact relationship-linked raster backgrounds/pictures, read-only decorative layout/master shapes and pictures, and unique placeholder geometry into the neutral presentation snapshot. Inherited decorative shapes also project the existing supported custom path commands and linear gradient fills. Canvas and thumbnail pixel tests verify layer order; inherited artwork does not enter the editable slide-shape collection. `TestPPTXLayoutMasterSamplesOpenAndRender` opens all four supplied PPTX files, checks their first slides, and verifies the source bytes stay unchanged. Inherited EMF pictures use `github.com/iEvan-lhr/emfToPng v0.0.2` (the module's `LICENSE` is Apache-2.0; its README says MIT). Since its parser does not bound reads to each record and allocates from record counts, `internal/format/pptx/emf.go` validates a 2 MiB input cap, 4,096-record cap, 8,192-pixel dimensions, 16-megapixel area, a bounded vector-record subset, and point/style counts before decoding; decoder panics fail closed. The three VCU EMFs in `PPT_RealTest.pptx` and its JPEG photo render, and a Gio pixel regression confirms the footer cover reaches the canvas. EMF text, bitmap records, other unrecognized EMF records, and broader OOXML artwork remain unsupported. Supported background-style fills are limited to solid sRGB/theme colors and PNG/JPEG/GIF raster assets. Groups/transforms, effects, gradient/pattern background styles, theme color transforms beyond `phClr`, and complete DrawingML semantics are not implemented, and no pixel parity with PowerPoint or LibreOffice is claimed.

#### Password-to-open encryption: no dependency selected

Inspected the exact pinned `github.com/xuri/excelize/v2 v2.11.0` implementation on 2026-10-03. `Encrypt` calls `standardKeyEncryption` and encrypts package blocks with AES-ECB; Standard encryption has no package-integrity HMAC. `Decrypt` recognizes Agile encryption, but its Agile path decrypts the package key and package without validating the encrypted password verifier or `dataIntegrity` HMAC. Do not route DOCX reads or writes through these APIs as a security feature.

Audited the exact `github.com/mgilbir/spine v0.3.1` tag (commit `4a39ee030412a9b04fa2b8439610b6cdce0eaa1a`) from source on 2026-10-04. Spine is pre-1.0, declares Go 1.25.0, and is MIT licensed; the project currently declares Go 1.27.0. Its `common/crypto.Encrypt` writes Agile AES-256-CBC/SHA-512 with `dataIntegrity`; strict `DecryptWithOptions` rejects missing/partial integrity data and HMAC mismatch, caps attacker-controlled `spinCount`, and returns both the detected scheme and an `IntegrityVerified` result. The isolated upstream package checks passed with `go test ./common/crypto ./opc -count=1` using a temporary module/cache, without adding Spine to this project. The optional upstream `msoffcrypto-tool` cross-validation was unavailable, and no Office-generated DOCX corpus was tested.

Do not use Spine's `opc.OpenReader` as the security-sensitive decrypt path: its encrypted-container helper accepts Standard/RC4 as well as Agile and discards the crypto result's scheme/integrity fields before returning a generic reader. A future adapter must inspect CFB streams and call `common/crypto.DecryptWithOptions` directly, then require Agile plus `IntegrityVerified == true`; the candidate CFB reader is `github.com/richardlehane/mscfb v1.0.9` (Apache-2.0, Go 1.18, with `msoleps v1.0.3`). Its source checks sector ranges and chain cycles and caps some table allocations at 64,000 entries. However, `mscfb.New` accepts an `io.ReaderAt` without a total-input limit, and directory traversal recursively follows untrusted links; an application-enforced file/stream/entry budget and adversarial depth tests are still needed. Required CFB streams must be selected unambiguously from that same parsed container before passing their bytes to Spine crypto. Spine's `opc.SaveEncrypted` writes Agile output and may be evaluated for the write side independently. Neither package requires LibreOffice or an Office process at runtime. No encryption dependency is selected until the CFB boundary, limits, strict read path, and Office interoperability are validated.

The integration boundary is broader than the file codec: `snapshotState` stores the full DOCX ZIP snapshot in the local SQLite workspace. A complete implementation must keep that recovery payload encrypted, re-prompt for the password on restore, and preserve encryption across Save, Save As, AutoSave, and Share. Do not enable File > Protect Document until the CFB/dependency boundary is reviewed and strict tamper, wrong-password, bounded-resource, and Office-compatible save/open checks pass across those persistence paths.

Sources: [Microsoft Agile data encryption](https://learn.microsoft.com/en-us/openspecs/office_file_formats/ms-offcrypto/9e61da63-8ddb-4c0a-b25d-f85d990f44c8), [Microsoft Agile integrity generation](https://learn.microsoft.com/en-us/openspecs/office_file_formats/ms-offcrypto/63d9c262-82b9-4fa3-a06d-d087b93e3b00), [Excelize v2.11.0 source](https://github.com/qax-os/excelize/blob/v2.11.0/crypt.go), [Spine v0.3.1 crypto API](https://pkg.go.dev/github.com/mgilbir/spine@v0.3.1/common/crypto), [Spine v0.3.1 OPC API](https://pkg.go.dev/github.com/mgilbir/spine@v0.3.1/opc), [mscfb v1.0.9](https://pkg.go.dev/github.com/richardlehane/mscfb@v1.0.9).

### Deferred third-party DOCX candidates

- **UniOffice** advertises existing DOCX read/edit operations, formatting, images, tables, and conversion features. Its project states that it is commercial and requires a license code. Consider it only if its license/price model is acceptable and corpus tests justify it.
- **godocx** and **fumiama/go-docx** describe Go APIs for reading and writing DOCX. Treat them as candidates for a limited workflow, not as evidence of broad Word fidelity. Review project activity, license, API coverage, and round-trip output for the exact fixture corpus before selection.
- **office_oxide Go binding** offers extraction/conversion APIs and limited editing methods such as text replacement and XLSX cell setting, according to its Go README. It calls a Rust core through cgo and requires the native library/header to be built or installed. Factor native build and distribution into the decision.

Sources: [UniOffice](https://github.com/unidoc/unioffice), [godocx](https://github.com/gomutex/godocx), [fumiama/go-docx](https://github.com/fumiama/go-docx), [office_oxide Go README](https://github.com/yfedoseev/office_oxide/blob/main/go/README.md).

### PDF generation: selected vector replay backend (integrated, visual acceptance remains open)

The controlled probe selected [`SalvioniDigitalSolutions/gopdf`](https://github.com/SalvioniDigitalSolutions/gopdf) for page boxes, vector paths, images, alpha masks, and PDF serialization. Pin: `v0.0.0-20260922202729-55a8f5fed5f5` (module checksum `h1:8D8Tk4WTPnSJTFdB172lkyBLlExzC/EysR1ECIx+QR8=`). Its module declares Go 1.22, has no third-party module requirements, and carries an MIT license. It is not a text-layout engine: `Page.Text` maps Unicode characters back through the font cmap and applies its own kerning; it has no public positioned-glyph-ID interface. Therefore visible text must not use `Page.Text` as the layout source.

Probe date: 2026-10-02. An isolated program used Go-text `v0.3.4` to resolve an outline from an actual glyph ID, replayed its quadratic/cubic segments as PDF vector paths at the shaped origin, and added an alpha-zero Unicode text layer for extraction. Results:

- Mixed `A中B` rendered visibly. The probe output was independently parsed by Poppler `pdfinfo` and rendered by Poppler `pdftoppm`; the generated page was 320 × 180 points and one page. Production package regressions now also render vector output and read text through `gopdf.Reader`; independent Poppler/PDFKit text extraction remains unverified.
- The generated probe PDF contained `/ToUnicode`; `gopdf.Reader.PageText(0)` returned exactly `A中B` for both regular text and the alpha-zero text-layer experiment. The in-project `TestWriteWordPDFExtractsMixedCJKLatinTextWhenSystemFontIsAvailable` verifies production export returns the same CJK/Latin string when `/Library/Fonts/Arial Unicode.ttf` exists on the host. The upstream module also tests embedded font ToUnicode output.
- A translucent NRGBA pixel survived PDF round trip: decoded alpha was `24672/65535` (96/255).
- `RenderPageDetail` reported 3 glyphs and 0 missing for the test; the outline replay and extraction overlay stayed aligned to the same page origin. The source font was the host-installed `/Library/Fonts/Arial Unicode.ttf`; its `OS/2.fsType` was `0x0008` (editable embedding). No font file is bundled or redistributed by this dependency decision. Production must check embedding permissions before adding the invisible searchable text layer; if a chosen font forbids embedding, export must report that limitation rather than silently embed it.
- Pure-Go probe code (`gopdf` + Go-text outline APIs) cross-built with `CGO_ENABLED=0` for macOS/arm64, Windows/amd64, and Linux/amd64. The app's Gio desktop package compiled on macOS/arm64 and Windows/amd64. Linux cross-compilation from this macOS host remains unverified because Gio excludes its Vulkan files when `CGO_ENABLED=0`; that is a host/toolchain limitation, not a gopdf limitation.

Production integration: `internal/format/pdf/word.go` replays each point-based scene's page box, vector glyph paths, highlights/underlines, table borders, and PNG/JPEG image rectangles/rotation. `Page.Text` is used only for a fully transparent Unicode search/copy layer; it does not determine visible geometry. `ExportWordPDFFile` writes a same-directory temporary file, reopens it to validate page count and each page size, then atomically replaces the target. The UI confirms layout warnings, flushes drafts, compares the exported DOCX snapshot with the accepted neutral blocks/layout projection, and checks a revision/draft epoch immediately before commit. Regression tests verify source DOCX snapshot and dirty state remain unchanged, and stale/canceled/failed work preserves an existing PDF.

Presentation PDF export uses the same pinned backend from `internal/format/pdf/presentation.go`, through `internal/format/presentationpdf`. It lays out projected text with the shared word-layout/font pipeline and replays supported solid shapes, custom paths, backgrounds, and raster images. The staged PDF is reopened and checked for page count and A4 dimensions, then linked to a previously nonexistent destination under the revision guard. This does not establish PowerPoint visual fidelity: animations, transitions, media playback, tables, gradients, unsupported paths, and unprojected OOXML are outside the export boundary. Build/static-analysis checks pass; a representative export still needs visual comparison.

Embedding is fail-closed: the writer reads `OS/2.fsType`, checks the requested TTC face, cmap coverage for each invisible text chunk, and the selected PDF backend's TrueType subsetting behavior. It rejects restricted embedding, bitmap-only embedding, missing permission tables, TrueType no-subsetting, and collection faces other than face 0. The host CJK fixture reports `fsType=0x0008`. Fonts that cannot be embedded currently block export; a nonembedded `ActualText` extraction fallback is not implemented. The in-project reader covers CJK/Latin extraction and visible vector rendering; independent Poppler/PDFKit text extraction and Pen/Glance Computer Use visual comparison remain pending. PDF integration is available for the declared layout subset but is not 1:1 acceptance evidence.

Other candidates remain unselected: `go-pdf/fpdf` is archived; `signintech/gopdf` carries a `gofpdi` dependency and its positioned-CJK path has not passed a project probe. Source review is not acceptance evidence.

### macOS print service: PDFKit/AppKit adapter implemented

`internal/printservice/print_darwin.go` and `print_darwin.m` accept in-memory PDF bytes, validate page count/options, copy the input for the Objective-C call, create a PDFKit document, and use AppKit's native print operation with page scaling disabled and auto-rotation off. Panel creation is dispatched to Cocoa's main queue so the Gio window-loop goroutine can continue polling job completion. `darwin/arm64` package tests/build pass. Computer Use opened the native panel and showed Page 1 of 1 and Copies 1, then canceled. In the current visual pass the bindable QA window displayed a blank DOCX (1 page, 0 words), not the Pen sample; the current `go run ./cmd/desktop` process itself could not be bound by CUA. Therefore this is evidence for the native panel path only, not matched-document page fidelity. The machine had no selected printer, so successful submission, virtual-printer copies/ranges, and paper dimensions remain unverified. Windows, Linux, and no-cgo builds return unavailable and keep Print disabled. The app does not start LibreOffice, a PDF viewer, or a command-line print program.

### 旧版 XLS：本地扩展 `github.com/extrame/xls v0.0.1`（Apache-2.0，已选用）

固定版本的上游模块采用 Apache-2.0 许可证且为纯 Go 实现；当前仍以它作为 BIFF 解析基础，在 `internal/format/xls/biff` 中维护仓库本地副本，并沿用上游模块路径。检查 v0.0.1 源码发现：`ReadAllCells` 会把工作表展平、将值格式化为字符串、丢失 XF 元数据，并把公式显示成字面文本 `FormulaCol`；解析记录时也会忽略错误，`WorkSheet.Row` 对不存在的行还会解引用空指针。因此项目需要扩展解析器，不能把上游 API 表面当作兼容性保证。

本地扩展按工作表和升序稀疏行公开原始数值、文本/布尔/错误值、公式 token 与缓存结果、空白单元格 XF 索引和工作簿 XF 记录；真实 BIFF `FORMULA` 后的 `STRING` 记录也会关联到对应公式，覆盖带中文的字符串缓存；`SHRFMLA`/`ARRAY` 记录会关联到 `PtgExp` 单元格。`internal/format/xls/reader_import.go` 会先扫描 OLE Workbook 流，拒绝 BIFF `FILEPASS`、校验记录边界，并在旧解析器物化工作表之前统计序列化单元格以执行 100,000 格预算。扫描器读取 `BOUNDSHEET` 可见性、`ROW` 行高/隐藏/分组/样式、`COLINFO` 宽度/隐藏/最佳适配/分组/折叠/XF、`MERGEDCELLS` 和注释元数据；转换器将这些可表示属性，以及公式和字体/边框/对齐/数字格式映射到暂存 XLSX；填充图案从 BIFF8 XF 的 Linecolor 位域解码，索引颜色在缺少 PALETTE 记录时使用完整内置调色板。隐藏表、合并区域、隐藏行列、行列格式及空文本批注均有转换或保存重开验证。LibreOffice 会为无绘图工作簿输出单独的空 `MSODRAWING` 标记，因此不把该标记本身误报为对象；空 `Note` 对象可以转换为 XLSX 批注，图表、其他绘图、表单控件以及带正文/富文本的批注仍会明确拒绝。超链接、零宽列、行折叠/phonetic/特殊边框标记、列 phonetic 和 `COLINFO` 默认列格式也会 fail closed。行/列位标记按微软 [MS-XLS Row](https://learn.microsoft.com/en-us/openspecs/office_file_formats/ms-xls/4aab09eb-49ed-4d01-a3b1-1d726247d3c2) 和 [MS-XLS ColInfo](https://learn.microsoft.com/en-us/openspecs/office_file_formats/ms-xls/2c339a18-0819-4221-9c5d-3e9cf304224b) 定义解码。公式解码器覆盖已验证的算术/比较/引用/区域/3D 及内置函数 token；解码接口可通过名称解析器支持定义名称，但当前 XLS 导入器尚未读取 BIFF `NAME` 表，因此引用定义名称的实际工作簿会明确报错。未知函数、外部定义名称、数据表公式和缺少关联记录的 `PtgExp` 也会明确报错。BIFF `PtgArray` 尾随常量、BIFF5 XF 样式尚不支持，不能静默当作常量或默认样式。SST 和 CONTINUE 解析按每条续段记录的字符编码标记处理文本分段；3,000 条唯一中文字符串的 LibreOffice BIFF 样本验证首尾文本和全部单元格。解析器对最多 100,000 个唯一字符串和 16 MiB SST 字节设置 fail-closed 上限，防止格式损坏或异常输入在工作簿打开前产生无界分配。根 `go.mod` 将上游模块替换为这个本地副本，并保留原许可证。

证据见 `internal/format/xls/reader_import_test.go`、`internal/format/xls/converter_test.go`、`internal/format/xls/formula_test.go`、`internal/format/xls/style_test.go` 和 `internal/format/xls/biff/import_test.go`，以及小型 `formula-style-multisheet.xls`、带真实字符串公式缓存的 `formula-string-cache.xls`、覆盖合并/超链接/行列元数据的 `unsupported-metadata.xls`、超出导入预算的 `resource-over-budget.xls`、`unsupported-chart.xls`、3,000 条中文共享字符串的 `sst-continuations.xls` 和 100,000 格密集数值/布尔 `benchmark-dense.xls` 样本。合并区域现在转换并保存；`unsupported-metadata.xls` 仍因其中的超链接而 fail closed。多表样本覆盖工作表顺序、原始小数值、公式缓存、稀疏的第 65,536 行/第 256 列、公式 token、带样式空白单元格以及转换后的行高和列宽。当前 `encrypted.xls` 只是用于检测 FILEPASS 的样本：它能验证解析器在遇到加密记录时提前拒绝，但记录之后的工作簿数据并未经过密码加密；它不能证明解析器可解密或打开密码保护的 XLS。损坏的非 OLE 输入和截断的 OLE 输入均有拒绝测试。桌面打开会在后台将 BIFF8 流式转换到应用私有磁盘暂存 `.xlsx`，再由正常 XLSX 适配器打开；暂存目录在工作簿加载后清理，活动工作簿仍由 Excelize 保存在内存中。`.xls` 原文件保持不变，编辑结果只可另存为 `.xlsx`，拒绝将其写回 `.xls`。`internal/desktopui/xls_open_test.go` 验证多工作表使用与 XLSX 相同的 `GridReader` 虚拟网格及标签布局，`internal/desktopui/xls_save_as_test.go` 覆盖 XLSX-only Save As 与源文件保护。

### Markdown: selected source parser and local math renderer

`github.com/yuin/goldmark v1.7.13` (MIT) is selected behind the neutral Markdown adapter. GFM and the built-in Footnote extension cover table alignment, task checkboxes, emphasis/deletion, links/linked images, nested lists/quotes and standard named footnotes. Literal code, punctuation escapes, entities, escaped dollars and currency have dedicated regressions. Source is retained independently of the AST, including BOM and CRLF; heading offsets use a linear source-line index. Parser objects never enter Gio state. See [Goldmark's primary documentation](https://github.com/yuin/goldmark).

`github.com/alecthomas/chroma/v2 v2.27.0` (MIT; Go 1.25 minimum; pure Go) supplies fenced-code syntax tokens behind the Markdown adapter. A fixed light palette becomes neutral literal code spans; lexer/token types never enter UI state. C# (`c#` alias), CSS, JavaScript and PHP snippets without an opening `<?php` have keyword-colour and exact-source regressions, including BOM, CRLF and Chinese. Unknown or absent language labels remain plain code. Highlighting accepts at most 1 MiB and 100,000 tokens, checks a 250 ms work budget between iterator calls, and relies on Chroma's 250 ms timeout for each regex match; this is not a hard total wall-clock deadline. Any limit, lexer failure or source mismatch returns the entire original text without partial highlighting. Tokenisation does not interpret Markdown links, images or formulas. Sources: [Chroma primary documentation](https://github.com/alecthomas/chroma), [v2.27.0 lexers](https://pkg.go.dev/github.com/alecthomas/chroma/v2@v2.27.0/lexers).

`codeberg.org/go-latex/latex v0.3.0` (BSD-3-Clause) supplies local math glyph rendering. The earlier GitHub project is archived; the maintained Codeberg module is selected. Evaluation found that the upstream renderer does not implement all script AST forms needed by the approved fixture corpus. A bounded adapter composition layer handles superscripts, subscripts, fractions and roots, with serialized upstream access and explicit diagnostics. Tests cover Greek/operator glyphs, scripts, fractions, roots, malformed expressions and unsupported commands. Accepted expression length is 4096 bytes, nesting depth 24, and output dimensions at most 8192 × 4096 pixels. These limits and tests support only the documented subset, not full TeX. See [module documentation](https://pkg.go.dev/codeberg.org/go-latex/latex).

PDF uses the already selected Word PDF/font/layout adapters. Markdown PDF regressions cover Chinese searchable text and images/formulas both in body and table cells. Unsupported resources fail before output replacement; a revision/draft/session guard prevents stale results from replacing an existing destination. Gio captures and the representative PDF were visually inspected on macOS arm64.

### PDF workspace adapter — 2026-10-07

Reuses the already pinned `github.com/SalvioniDigitalSolutions/gopdf` at `v0.0.0-20260922202729-55a8f5fed5f5`; no new PDF dependency. Third-party reader/update/render types stay inside `internal/format/pdfdoc`; UI consumes neutral `document.PDFPage`, `PDFInfo` and `PDFCommand`.

The canonical state is a validated PDF package revision. Commands apply an incremental update, serialize and reopen before publication. Rendering uses an immutable package snapshot; raster pixels and hit data carry the same revision. Tests cover text edit/no-op/stale command, notes/highlights/ink, rotation, save/reopen, unchanged second page, existing notes, undo/redo and failed-save dirty preservation. UI tests cover shared model identity, recovery, stale scenes and visible canvas pixels at two window sizes.

API availability is not a compatibility guarantee. Current text-fragment API does not expose every graphics-state transform/opacity needed for safe arbitrary editing. Consequently pages with ExtGState/XObject resources, invisible text and rotated text are restricted; signed PDFs reject mutations, and encrypted/repaired files reject opening. Text replacement depends on the original font encoding and does not reconstruct paragraphs. Native printing is integrated but not hardware-verified. See `office-support.md` for the maintained boundary.

Native render fallback: macOS/cgo uses CoreGraphics/CoreFoundation when the pure-Go renderer reports missing glyphs or an error, and when a page paints a JPEG 2000 (`/JPXDecode`) image that the current Go renderer silently skips. The latter is detected from the page's used image objects before rendering. The renderer receives in-memory bytes of the accepted model revision, never reopens the source path. Annotation appearances are composited from a temporary, unsaved rendering projection of that same revision. Geometry regression checks 1× and 2× placement. This is a platform rendering backend, not a separate editing model; non-macOS builds retain the Go renderer and return an explicit page-render error for JPEG 2000 pages rather than displaying them as blank. The local SimSun-embedded Chinese PDF and the DaoQin JPEG 2000 scan sample exposed these fallback cases.

### PDF snapshot backing and workspace streaming — 2026-10-21

The selected PDF package remains gopdf `v0.0.0-20260922202729-55a8f5fed5f5`. `pdfdoc.Open` and `OpenSnapshotStream` copy accepted bytes into a private temporary file, then use read-only `syscall.Mmap`/`Munmap` on macOS and Linux. The mapping owner is held by `pdfdoc.Document`, whose close clears reader/current/saved/history references before unmapping. The temporary pathname is removed after mapping; the active document retains no linked temporary file. Other targets use a compatibility implementation that reads the temporary backing into a Go byte slice, so that path does not provide the same heap reduction.

Workspace PDF restore uses the already pinned `modernc.org/sqlite v1.59.0` low-level `modernc.org/sqlite/lib` API together with `modernc.org/libc`: a read-only, full-mutex connection pins a SQLite read transaction, resolves the document row, and streams `sqlite3_blob_open` / `sqlite3_blob_bytes` / `sqlite3_blob_read` in 1 MiB chunks into the PDF temporary snapshot. The signed 32-bit BLOB size/offset interface limits this path to 2,147,483,647 bytes. It does not select the payload through `database/sql`, hydrate `Collection.Session.Payload`, or change the database schema.

Workspace writes use `PDFInfo.Revision` before requesting bytes. If the SQLite snapshot is already at that revision, only dirty/view metadata is updated; otherwise `SnapshotWithRevision` captures bytes, revision and dirty state under one adapter read lock, and the persisted revision advances only after the SQLite update succeeds. Per-shared-session serialization prevents concurrent windows from duplicating or reordering checkpoints. This reduces full-payload Go heap copies during reopen and view-only saves; it does not promise a proportional reduction in macOS process footprint because resident mapped pages, parsed PDF structures, undo revisions, rendered images, font caches and GPU allocations may remain resident. The non-mmap target fallback retains the full package in Go memory.

Evidence: `internal/format/pdfdoc/snapshot_backing_test.go`, `internal/workspace/store_payload_stream_test.go`, `internal/workspace/collection_payload_metadata_test.go`, and `internal/desktopui/pdf_workspace_mmap_test.go` / `pdf_workspace_persistence_test.go`. The bounded restore, exact bytes, source immutability, changed and undone snapshots, injected SQLite write failure and shared mapping lifetime are covered. Build and live process-footprint measurements are tracked separately from adapter correctness; a heap profile alone does not include mmap residency or native/GPU allocations.

### PDF merge/split utility — 2026-10-28

The utility reuses the same pinned gopdf version; it adds no PDF dependency. `internal/format/pdfdoc/utility_files.go` keeps `gopdf.Reader` and `gopdf.Document` behind the format adapter, uses `Document.ImportPage(reader, pageIndex)` to assemble pages in requested order, and writes via `Document.WriteTo`. Each staged output is reopened through `pdfdoc.Open`, checked against its expected page count, and committed with `fileutil.MoveExclusive`; an existing destination is rejected. `internal/application/pdf_utility.go` exposes only neutral metadata, ranges, modes and output paths to the desktop UI.
